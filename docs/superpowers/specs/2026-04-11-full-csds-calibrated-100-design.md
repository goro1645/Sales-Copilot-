# Full-CSDS Calibrated-100 Design

## Goal

Build a `100`-case calibrated benchmark from the `full-csds` `test` split so we have an evaluation set that is more independent than the current auto-generated weak gold and can better judge whether Sales Copilot outputs are semantically correct at the field level.

## Problem

The current `full-csds` `test 800` benchmark is generated by adapting CSDS summary fields into `expected_parse` with local rules. That benchmark is still useful for large-scale trend tracking, but recent audits showed clear structural issues:

- `budget_signals` often overlaps with `next_steps`
- `timeline_signals` may contain full customer-service reply sentences rather than pure time signals
- some fields reflect rule-generated phrasing rather than independently verified business semantics

This creates an evaluation loop where we partly judge the model by how closely it matches our own adaptation rules. To break that loop, we need a smaller independently reviewed benchmark derived from the same source split but calibrated by case review rather than auto-gold rules alone.

## Scope

This design covers creation of a `100`-case calibrated subset from `full-csds test`, including sample selection, AI-assisted pre-annotation, human review hooks, and export of a final benchmark file.

In scope:

- stratified selection of `100` cases from the `full-csds` `test` split
- preservation of raw source context (`meeting_note_text`, `UserSumm`, `AgentSumm`, `FinalSumm`)
- preservation of auto-generated `expected_parse` for reference
- AI-assisted pre-annotation of the key parse fields
- explicit human-review metadata for risky cases
- export of a working review file and a final calibrated benchmark file

Out of scope:

- changing the main Sales Copilot workflow
- changing the `full-csds 800` weak benchmark scoring logic
- building a GUI review tool
- training a new model on the calibrated set

## Sampling Strategy

The calibrated subset should be stratified by review value rather than pure randomness. Target size is `100` cases with these buckets:

1. `ordinary_stable`: `25`
   - relatively clear customer-service cases
   - limited `budget_signals` / `timeline_signals`
   - useful as baseline, non-edge samples

2. `timeline_boundary`: `20`
   - contains explicit time expressions
   - likely to blur time signals with action sentences

3. `budget_boundary`: `20`
   - contains refund / coupon / price-protection / compensation / price-related content in raw summaries or meeting-note text
   - likely to blur economic signals with generic customer-service responses

4. `field_overlap_high_risk`: `20`
   - auto-gold contains likely overlap between:
     - `timeline_signals` and `next_steps`
     - or `budget_signals` and `next_steps`

5. `model_rule_conflict`: `15`
   - cases where baseline parse output and auto-gold differ materially
   - or cases already known to produce strong disagreement between refinement variants and auto-gold

Sampling should be deterministic so the calibrated set is reproducible.

Bucket assignment should not depend solely on the existing auto-gold fields. In particular, `budget_boundary` cases should be identified from raw CSDS text and summaries using budget-like cues even when `auto_expected_parse["budget_signals"]` is empty, because prior audits showed that the weak gold does not surface this bucket cleanly.

If a target bucket does not have enough eligible rows, the sampler should deterministically backfill from the closest ambiguity-heavy bucket rather than silently shrinking the dataset. Preferred fallback order is:

- `budget_boundary` -> `field_overlap_high_risk`
- `timeline_boundary` -> `field_overlap_high_risk`
- `model_rule_conflict` -> `field_overlap_high_risk`
- `ordinary_stable` -> remaining non-selected ordinary rows

## Review Targets

The calibrated benchmark should only focus on the fields that currently matter most for parse quality and gold drift:

- `confirmed_needs`
- `budget_signals`
- `timeline_signals`
- `next_steps`

The following fields stay unchanged unless there is an obvious issue discovered during review:

- `account_name`
- `customer_roles`
- `competitors`

## Annotation Workflow

This should be an AI-assisted pre-annotation workflow with human review, not a claim of fully manual first-pass labeling.

### Step 1: Build review-ready sample

For each sampled case, preserve:

- `case_id`
- `source_uid`
- `source_split`
- `sampling_bucket`
- `meeting_note_text`
- `user_summ`
- `agent_summ`
- `final_summ`
- `auto_expected_parse`
- `baseline_parse_result`

### Step 2: AI-assisted pre-annotation

For each sampled case, generate a `pre_annotation` object that includes:

- field-level decisions:
  - `keep`
  - `edit`
  - `drop`
- a `corrected_expected_parse` for the four target fields
- review metadata:
  - `confidence`
  - `needs_human_review`
  - `review_reason`
  - `review_note`

The pre-annotation is intended to reduce human review effort, not to replace it.

### Step 3: Human review

Human review should focus on cases where:

- `needs_human_review = true`
- field boundaries are ambiguous
- `budget_signals`, `timeline_signals`, and `next_steps` conflict
- auto-gold and baseline parse disagree in a meaningful way

In practice, the first review round is expected to focus on roughly `20-30` higher-risk cases rather than redoing all `100` from scratch.

## Review Record Structure

The working review file should keep both context and editable review fields. Each record should contain:

- source context fields
- `auto_expected_parse`
- `baseline_parse_result`
- `pre_annotation`
- `human_review`

`pre_annotation` should look like:

```json
{
  "confirmed_needs_decision": "keep",
  "budget_signals_decision": "edit",
  "timeline_signals_decision": "keep",
  "next_steps_decision": "edit",
  "corrected_expected_parse": {
    "confirmed_needs": [],
    "budget_signals": [],
    "timeline_signals": [],
    "next_steps": []
  },
  "confidence": "medium",
  "needs_human_review": true,
  "review_reason": "budget_next_step_overlap",
  "review_note": "Auto-gold mixes coupon restriction with general service response."
}
```

`human_review` should be initially blank in the working file and later filled during manual verification.

## Final Benchmark Export

The final calibrated benchmark should be exported to a clean JSONL file that is directly consumable by the existing parse-only evaluation runner.

Suggested path:

- `D:\minimind\.worktrees\minimind-job-agent\evals\sales_copilot\full_csds_calibrated_100.jsonl`

Each final row should contain:

- `case_id`
- `meeting_note_text`
- `expected_parse`
- optional source metadata needed for traceability

The final exported file should not require the review metadata to run evaluation.

## Outputs

V1 should produce two artifacts:

1. `full_csds_calibration_working_100.jsonl`
   - review-ready file with raw context, auto-gold, baseline parse, pre-annotation, and editable human review fields

2. `full_csds_calibrated_100.jsonl`
   - final benchmark file with calibrated `expected_parse`

## Success Criteria

This work is successful if:

- we can reproducibly generate a `100`-case calibration working set from `full-csds test`
- the sample covers both stable cases and high-value ambiguity buckets
- each row contains enough context for efficient review without reopening the raw dataset
- AI-assisted pre-annotation reduces manual effort while clearly marking cases that still need review
- the final calibrated file can be used as an independent benchmark file separate from the weak `full-csds 800` benchmark

## Expected Outcome

After this work, the project should have a two-tier evaluation story:

- `full-csds 800` remains a large-scale weak benchmark for trend tracking
- `full_csds_calibrated_100` becomes a smaller, higher-trust benchmark for judging real semantic quality

This will let us evaluate new parsing strategies without being locked into the exact behavior of the current auto-gold rules.
